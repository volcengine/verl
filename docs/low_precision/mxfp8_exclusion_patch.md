# Opt-in MXFP8 exclusion patch

Last updated: 10/13/2026

## Status and scope

The parser/matcher patches are registered in `build_fp8_method_patchers()` and
installed through the existing `apply_vllm_quant_patches()` lifecycle. This does
not add CUDA MXFP8 rollout support to `main`: the MXFP8 feature branch must still
mark its generated configs explicitly. Without that marker behavior is unchanged.

vLLM's `ModelOptQuantConfigBase.is_layer_excluded()` (0.24 to 0.29) includes a legacy
substring fallback. A router exclusion such as `model.layers.0.mlp.gate` also
matches the dense SwiGLU `model.layers.0.mlp.gate_up_proj`. Both HF projections
(`gate_proj` and `up_proj`) can consequently remain unquantized in rollout.
The upstream comment about ModelOpt 0.39 is not a runtime version guard.

`build_mxfp8_exclusion_patchers()` supplies two wrappers on the
`ModelOptMxFp8Config` subclass: `from_config()` transfers the explicit opt-in to
the parsed instance; `is_layer_excluded()` uses strict matching only when that
instance is marked. Unmarked configs call the original matcher. The ModelOpt
base class, other quantization classes, and `get_quant_method()` are untouched.

## Integration contract for the MXFP8 feature branch

1. Only when verl itself generates an online MXFP8 HF quantization config, add
   `_verl_exact_mxfp8_exclusions: true`. Do not add this marker to loaded user or
   checkpoint configs. Keep all real router/high-precision exclusions; this helper
   fixes matching, not router discovery across model architectures.
2. Install the common patches BEFORE vLLM parses that raw HF config. The parser
   wrapper explicitly saves the boolean marker; upstream normalization need not
   preserve unknown dictionary fields. Patching only after parsing loses provenance.
3. In **each model-building worker**, install the common patches before creating
   linear/MoE layers. Parsed configs carry only a boolean marker across serialization,
   not instance-bound methods. Existing worker startup installs the common patches;
   feature-branch integration must verify this also holds on its MXFP8 paths.
   A driver-only patch or a post-refit call is insufficient.

```python
from verl.utils.vllm.mxfp8_exclusion_patch import VERL_EXACT_MXFP8_EXCLUSIONS
from verl.utils.vllm.vllm_quant_utils import apply_vllm_quant_patches

# Future integration: ONLY the config generated by verl for online MXFP8.
hf_quant_config = {
    "quant_method": "mxfp8",
    "ignored_layers": ["model.layers.0.mlp.gate", "lm_head", "model.embed_tokens"],
    VERL_EXACT_MXFP8_EXCLUSIONS: True,
}

# In the launcher, BEFORE creating/parsing the vLLM config:
apply_vllm_quant_patches()
# Pass hf_quant_config through hf_overrides["quantization_config"].
# Each model-building worker must also call apply_vllm_quant_patches().
```

The example lists one layer for brevity; production integration must supply its
complete policy and the actual raw config corresponding to the parsed instance.
The marker is an explicit opt-in, not authentication or automatic proof of origin.
The caller owns provenance. The common registry owns installation/idempotence
via its existing `fp8_state.vllm_patches` guard. Builders return unstarted patchers,
not independently installed global state. Invalid marked configs raise instead
of silently leaving the legacy matcher active. The former instance-bound helper
is replaced by these registered wrappers; no per-instance installation is needed.

## Matching contract

- An ordinary entry matches a module when it equals a run of whole dot-separated
  components of the module's name: `lm_head` matches `lm_head` and
  `language_model.lm_head`, `model.layers.0.mlp` matches its descendants such as
  `model.layers.0.mlp.down_proj`, but `model.layers.0.mlp.gate` does not match
  `model.layers.0.mlp.gate_up_proj` and `lm_head` does not match `lm_head_extra`.
  This keeps what the legacy substring fallback got right and drops only matches
  that cut through a component. Wrapped names matter in practice: vLLM remaps
  exclusions with the model's `hf_to_vllm_mapper`, whose rule `"lm_head."` →
  `"language_model.lm_head."` (46 multimodal models in 0.29) does not apply to a
  bare `lm_head`, so a VLM's `language_model.lm_head` is reached only by component
  matching; an exact-only matcher would quantize it.
- Case-sensitive `fnmatch`-style globs are supported, not `re:` expressions.
- Patterns are evaluated against the fused runtime name and its HF shard names.
  Literal matches are passed to vLLM's `is_layer_skipped()` so all-or-none shard
  validation is preserved (including mixed exact/glob exclusions).
- An explicit exclusion of the fused module applies to the whole module.
- The upstream helper's specialized fused-expert-group handling is retained;
  this is not a new per-expert precision policy.
- Current `exclude_modules` and `packed_modules_mapping` are read on each call;
  the helper does not cache exclusion decisions or change the weight-sync cache.

## Validation

```bash
python -m pytest tests/utils/test_mxfp8_exclusion_patch_on_cpu.py -q
```

CPU tests use lightweight vLLM doubles and check the 28-layer/56-HF-parameter
collision, router preservation, instance isolation, legacy checkpoint behavior,
explicit opt-in, invalid inputs, fused shards, globs, parser propagation, config
serialization, registry integration, restoration, and old-vLLM fallback. They do not
establish GPU kernel correctness or that the feature branch installed the helper
in the correct worker.

Before deployment, validate against the installed vLLM matcher and then rebuild
the engine: check `gate_up_proj.quant_method`, weight dtype and scales on B200,
check initial and post-training refits, and ensure engine recheck no longer finds
the 56 gate/up discrepancies. Include a real MoE router regression and retain the
refit self-check. Updating only an already-built model's config cannot rebuild
its BF16 layers as MXFP8 layers.
