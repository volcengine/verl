Process Rewards in the v1 Trainer
================================

Last updated: 10/21/2026.

The v1 TransferQueue trainer supports optional process scores for intermediate
assistant turns. They shape actor advantages **after** the existing outcome
advantage estimator runs. They do not replace outcome rewards, change GRPO group
normalization, or modify critic returns. The feature is disabled by default.

This interface is for agent-provided feedback or custom task scorers. It does
not include a pretrained process reward model or infer success from tool text.

Enable process rewards
----------------------

An agent that already knows the score of each generated turn can provide the
standard ``turn_rewards`` field without implementing a scorer:

.. code-block:: python

   output.extra_fields["generated_turn_spans"] = [(0, 2), (4, 6)]
   output.extra_fields["turn_rewards"] = [-1.0, 0.5]

.. code-block:: yaml

   trainer:
     use_v1: true
   algorithm:
     process_reward:
       enabled: true
       mode: additive
       weight: 0.1
       scorers: []

The worker broadcasts each scalar to that turn's generated tokens. For example:

.. code-block:: text

   response_mask:          [ 1,  1, 0, 0,   1,   1]
   generated_turn_spans:   [(0, 2), (4, 6)]
   turn_rewards:           [-1.0, 0.5]
   process_scores:         [-1, -1, 0, 0, 0.5, 0.5]

``turn_rewards`` takes precedence whenever the key exists, including an all-zero
list. It must contain exactly one finite scalar per retained generated turn.
``None``, a wrong shape/count, or NaN/Inf rejects the trajectory rather than
falling back to a scorer. Per-scorer weights do not apply to this input; the
global ``algorithm.process_reward.weight`` still applies during shaping.
Configured scorers are instantiated when the worker starts, so remove unused
scorers rather than leaving invalid import paths in the configuration.

Turn boundaries and truncation
------------------------------

``response_mask`` marks whether a token was generated by the model.
``generated_turn_spans`` additionally identifies which generation produced it.
The latter contains ordered, non-overlapping, half-open response-token ranges
that cover all generated tokens and exclude tool/context tokens.

Without explicit spans, contiguous runs of ``response_mask == 1`` define the
turns. This fallback cannot distinguish adjacent generations, so a custom loop
with adjacent turns should always supply explicit boundaries.

The built-in ToolAgentLoop records boundaries across Continuous Token merges,
including inserted non-generated boundaries and removed suffix tokens. It clips
spans and any supplied turn rewards when the final response is truncated. A
partly retained turn keeps its score; turns with no retained generated tokens
are absent from the final spans. Feedback supplied by a custom agent must match
the retained spans. Do not use ``num_turns`` as the reward count: that field also
counts user and tool turns.

Custom scorers
--------------

When ``turn_rewards`` is absent, configure one or more subclasses of
``verl.trainer.ppo.process_reward.BaseProcessScorer``:

.. code-block:: python

   from verl.trainer.ppo.process_reward import BaseProcessScorer, generated_turn_spans

   class ActionScorer(BaseProcessScorer):
       async def evaluate(self, output, span, context):
           spans = generated_turn_spans(
               output.response_mask, output.extra_fields.get("generated_turn_spans")
           )
           turn = spans.index(span)
           # Task-defined structured feedback, one entry per retained turn.
           failures = output.extra_fields["failed_actions_per_turn"][turn]
           return -float(failures)

.. code-block:: yaml

   algorithm:
     process_reward:
       enabled: true
       mode: additive
       weight: 0.1
       scorers:
         - path: my_package.scorers.ActionScorer
           weight: 1.0
           kwargs: {}

``evaluate(output, span, context)`` receives the complete trajectory and the
sample's input fields. Return a finite scalar, broadcast to the turn, or a
one-dimensional vector of length ``end - start``. The runner sums
``scorer.weight * result`` for each turn. Scorers run sequentially and may await
external services; their timeout, retry and concurrency policy belongs to the
task. They must not mutate the output or keep per-sample mutable state in a
shared scorer instance.

The class and its dependencies must be importable on every rollout worker.
Neither a missing scorer nor invalid scores are silently replaced by zero.
Represent a legitimate neutral turn explicitly as zero. Distinguish model
action failures from infrastructure failures in the task protocol.

Advantage shaping modes
-----------------------

Let ``A`` be the original outcome advantage and ``r = weight * process_scores``.
Only generated-token positions contribute to the shaped actor advantages.

``additive``
   Use ``A + r``. Negative process scores reduce the advantage, but do not
   necessarily make a positive advantage negative.

``gvpo``
   Treat ``r < 0`` as a failure flag. On failed tokens, advantages below
   ``-zero_eps`` are multiplied by ``1 + negative_scale``; advantages within
   ``[-zero_eps, zero_eps]`` become ``-zero_penalty``; positive advantages above
   ``zero_eps`` become zero. Other generated tokens retain their advantages.
   Defaults are ``negative_scale=0.2``, ``zero_penalty=0.4``, ``zero_eps=1e-6``.
   Increasing a negative score's magnitude does not increase this penalty.
   This is a shaping rule on the existing estimator, not a full algorithm
   reproduction that changes normalization or the policy loss.

``process_weighted``
   Require ``r`` in ``[0, 1]``. Nonnegative advantages become ``A * r``;
   negative advantages become ``r`` where ``r > 0`` and otherwise stay unchanged.
   Define neutral/success scores carefully: zero suppresses nonnegative
   advantages in this mode.

Transport and observability
---------------------------

The worker scores each completed trajectory only when enabled and not running
validation, then transfers ``process_scores`` as a separate float32 response-token
field. Padding and tool/context tokens have score zero. The trainer retrieves
this field with the original reward/advantage inputs and shapes advantages
after estimation, leaving reward tensors and returns intact. Tokens rejected by
rollout correction are also excluded from process shaping and process metrics. An invalid score
fails the prompt through the existing worker failure path.

``process_reward/score_mean`` is the generated-token mean before the global
weight. For scorer inputs it already includes per-scorer weights. It is not an
outcome reward or the average GVPO advantage change. GVPO also logs
``process_reward/gvpo_{failed,negative,zero,positive}_token_fraction`` with all
generated tokens as the denominator; the three advantage branches sum to the
failed fraction.

Validation skips this scoring path. Persist task execution status separately
if evaluation needs error rates or other process metrics. The interface does
not automatically turn tool-return values into process rewards, add process
scores to the reward function, or perform an optimizer update after each turn.

CPU verification
----------------

The CPU tests exercise scorer/direct-input alignment, Continuous Token edits,
truncation, TQ publication and post-estimation advantage/return behavior:

.. code-block:: bash

   python -m pytest -q \
     tests/trainer/ppo/test_process_reward_on_cpu.py \
     tests/experimental/agent_loop/test_process_rewards_on_cpu.py

   python -m pytest -q \
     tests/trainer/ppo/v1/test_agent_loop_tq_on_cpu.py \
     tests/trainer/ppo/v1/test_trainer_base_on_cpu.py -k process

These checks validate the data path and numerical rules. They do not establish
task-accuracy improvements; those require controlled training/evaluation runs.
